# Photos view: decisions behind search, selection and Send to

Settled with Bob from the "Household Photos Wireframe". The README describes what the view does; this records why, and what is deliberately not there.

- **Already in the pipeline is hidden by default.** A photo whose original is a source of any photo in the library is left out of the timeline and search. "Show photos already in the pipeline" (search filters, Library group) shows them again, tagged "In pipeline" (green).
- **One processed photo per original, for now.** A send skips any original already in the pipeline. A second processed version of the same original is not supported: intake skips every asset id it already knows (`known_source_ids`), so allowing it needs an intake change.
- **The mark is derived, never stored.** It is worked out from the library each time (`household.pipeline_states`), so it clears when the processed photo is deleted for good, and a restore from the web trash brings it back.
- **In the pipeline's trash.** Such a photo is tagged "In trash" (amber). Choosing a Send to destination opens a dialog offering to send and purge. It is one request (`/api/household/send` with `purge: true`): the original is added to the entry queue first, and only if that worked (or it was already waiting there) are the processed photos made from it deleted for good (a collage goes as a whole), which makes the original eligible again. A send that is refused or skipped never purges, so a failed send cannot cost anyone a processed photo. The original is never touched.
- **A leftover original in an entry album.** If an original could not be cleared from its entry album (Immich lets only the account that added it do so) and its processed photo is then purged, the next cycle would process it again. Not handled.
- **Trash on any household photo** goes to the Immich trash of the account that owns it, after a confirmation. The pipeline's own copies are not touched. Sending and trashing use the owner's key (`IMMICH_EXTRA_API_KEY`), because Immich only lets an owner add their photo to an album or trash it.
- **Naming.** The third destination is "Import Only" (the app's name for it; the wireframe said "Importer").
- **People filter** is empty until Immich has named people (the face rebuild).
- **Search with words shows the best match first.** A Context search (what the photo looks like) with words, with or without filters such as people, keeps Immich's order and is drawn as one run of photos with no month headings or timeline, because sorting it by date buried the best matches ("boat pictures" with two people picked looked like every photo of those two). Every other search (file name, description, folder, text in the picture, or filters alone) stays newest first by month, with its timeline.
- **Collage Maker is a place, and nothing is grouped automatically.** The old rule (a portrait waits for a second one, then 2 or 3 are grouped) is gone from intake, tests, the README and the recipe, along with the "waiting for a partner" status. Photos in the Collage Maker album only wait until a person selects 2 to 12 and presses Make collage. Landscape and portrait can be mixed.
- **Claude chooses the layout per set** (recipe section 7): one shared mat, a 16:9 canvas and balanced sizes are fixed; the arrangement is not. It can be changed afterwards in the photo's chat.
- **Sources are in the order selected.** The place sends the ids in click order and the collage records them that way; the recipe reads that order as the reading order. The collage is named after its first source, like every collage.
- **What was built the same as search results.** The waiting list is drawn with the search-results machinery (months, days, its own timeline), not the flat rows of the wireframe. It is the whole album at once (no paging), without videos and without originals the pipeline already knows.
- **Remove only touches the Collage Maker album.** The photo stays in its owner's library. Each configured key is tried in turn, because Immich lets only the account that added a photo take it out of an album; photos that none can remove are reported with the reason.
- **Videos in the album are still recorded as failed** (unchanged), so they do not wait for ever; they cannot go in a collage.
- **The sidebar count is cached for 10 seconds** on the server (and dropped on any change made here), so keeping the page open does not ask Immich every few seconds. It is left off when Immich cannot be asked.
- **Thumbnails are drawn in their native shape.** The library places (Queue, Review, Live, albums, Trash) use the same justified rows as Photos, each tile sized by the photo's width-to-height ratio; squares were dropped. `/api/photos` returns `ratio`, read from the image header (EXIF orientation applied) and cached per revision file, which never changes. A video, or an image that can't be read, has no ratio and is drawn 3:2.
- **Back closes the top layer.** The viewer, an enlarged picture, a confirmation dialog and the Auto-delete editor each push a history entry, so the browser's Back button (and a phone's back gesture) closes the topmost one instead of leaving the page. Places keep their own addresses (`/#review`, `/#photos`).
- **Not built yet:** editing tools.
- **Unverified against a real Immich:** the search request fields (`ocr`, `isNotInAlbum`, `visibility`, `personIds`, `lensModel`), `/search/suggestions`, `/people` and `/download/archive`. Checked only against a fake.
